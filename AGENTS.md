# NutriCal — Agent Notes

Personalized daily macro/micronutrient targets app (Expo + React Native + TypeScript). Full spec: `project-docs/PRD.md`. See `README.md` for stack, structure, and current status.

Key constraints to respect when working in this repo:

- **No accounts, no backend, no cloud sync.** Profile data is local-only (`AsyncStorage`). Don't add a server or auth system without an explicit request — this is a deliberate v1 decision (PRD §8.1, §12, §13).
- **Calculation engine (`src/engine`, `src/data/dri`) must stay pure and unit-tested.** It's the credibility core of the product (PRD §10, §14) — no UI concerns leaking in, no unvalidated formula changes without updating/adding tests in `__tests__`.
- **DRI micronutrient data (`src/data/dri/adultBrackets.ts`, `adolescentBrackets.ts`) covers ages 9+ (both sexes) but is still explicitly flagged as needing verification against the NIH ODS DRI tables** before it's treated as production-accurate — don't assume it's audited. Ages below `MIN_SUPPORTED_AGE` (9, exported from `src/data/dri/index.ts`) and pregnancy/lactation life stages are not seeded at all.
- **Tone/design:** plain-language, non-judgmental, no red/green alarm framing (PRD §11.1). Light mode = white + green accent; dark mode = navy + green accent (PRD §11.2) — colors in `src/theme/colors.ts` are WCAG AA-validated (see the audit comment at the top of that file); don't change a hex value without re-running `src/theme/__tests__/contrast.test.ts`.
- **Freemium boundary:** macros are always free; micronutrients are premium-gated and shown to free users as a locked, name-only teaser (PRD §7, §8.4) — don't leak micronutrient values to free users in UI work.
- **Profile persistence goes through `src/storage/profileStorage.ts` only** — screens/state should call `saveProfile`/`loadProfile`/`clearProfile` rather than touching `AsyncStorage` directly, so the storage format changes in one place.
- **Units:** onboarding height/weight input is imperial-first (ft/in, lb) with a metric toggle. Internal storage (`UserProfile.heightCm`/`weightKg`) is always metric — convert at the UI edge (`src/onboarding/unitConversion.ts`), not in the engine or storage layer.
- **Two separate state layers, don't conflate them:** `OnboardingDraftContext` (in-memory only) holds in-progress answers *during* the onboarding wizard; `ProfileContext` (backed by `profileStorage`) holds the one real, saved `UserProfile` the rest of the app reads. Only the final onboarding screen (`GoalScreen`) should ever call `saveProfile` to turn a draft into a real profile.
- **`AppSettingsContext` (`src/settings/AppSettingsContext.tsx`, backed by `src/storage/appSettingsStorage.ts`) is a third top-level context**, sitting above `ProfileContext`/`OnboardingProvider` in `App.tsx` (inside `SafeAreaProvider`) — same split as everywhere else in this repo: pure types/defaults in `src/settings/appSettings.ts` (unit-tested), a thin untested React context exposing `{ settings, isLoading, setUnits, setAppearance }`. It holds `units` (`'imperial' | 'metric'`) and `appearance` (`'light' | 'dark' | 'system'`), both defaulting to today's de-facto behavior (`imperial`, `system`) so no existing install sees a change until the user visits Settings. `useTheme()` (`src/theme/index.ts`) reads `appearance` and only falls back to `useColorScheme()` when it's `'system'`. The Height/Weight onboarding screens seed their local unit toggle from `settings.units` and call `setUnits(...)` on change, so a preference set in either place (onboarding or Settings) stays in sync everywhere else — don't reintroduce a hardcoded `'imperial'` default on a screen with a unit toggle. **This is not what "Delete my data" clears** — see the Settings screen note below.
- **The Settings screen (`src/screens/SettingsScreen.tsx`) is a modal reached via `GearButton` (`src/components/GearButton.tsx`, an outlined `Ionicons` `"settings-outline"` glyph) placed top-right on `ResultsScreen` only** — there's no per-screen native header in this app (`headerShown: false` everywhere), so the icon is a hand-positioned absolute sibling offset by `useSafeAreaInsets().top`, same pattern as `CelebrationBanner`. Its "Delete my data" action calls `clearProfile()` + `clearDismissedNudgeTimestamp()` only — it deliberately does **not** touch `AppSettingsContext`'s units/appearance preferences, since those are app configuration, not the sensitive body-metric "your data" PRD §13 is about. Its "Edit profile" row shares `useEditProfileNavigation()` (`src/profile/useEditProfileNavigation.ts`) with `ResultsScreen`'s own "Edit profile" link — if you change that flow, edit the shared hook, not one call site.
- **Editing an existing profile reuses the onboarding wizard.** `ResultsScreen.handleEditProfile` calls `hydrateFromProfile` on `OnboardingDraftContext` to seed the draft from the saved profile, then navigates forward to `Sex` — it does **not** call `clearProfile`. The saved profile stays intact (and non-null) for the whole edit, only getting overwritten if the user reaches `GoalScreen` and finishes. Each onboarding screen already initializes its local input state from `draft.*`, so this prefills automatically. `GoalScreen` derives `isEditing` from `useProfile().profile !== null` — true only during a re-edit (it's null during first-time onboarding) — to swap its button label to "Save changes." If you add a new onboarding screen/field, make sure it also seeds from `draft` on mount and that `hydrateFromProfile` copies that field, or edits will silently drop it.
- **`RootNavigator`'s initial route depends on `ProfileContext.isLoading`/`profile`** — don't add new "first screen" logic elsewhere; that's the one place that decides Welcome vs. Results on launch.
- **`OnboardingScreenLayout` wraps every onboarding step in `KeyboardAvoidingView`** (`padding` on iOS, `height` on Android) so the pinned footer button and any focused `TextInput` (Age/Height/Weight) stay above the on-screen keyboard. This is applied on Android too, deliberately — don't assume Android's default `windowSoftInputMode="resize"` is sufficient on its own; Expo's app config docs note it can misbehave combined with the default translucent status bar. If you add a new onboarding screen with a `TextInput`, build it on `OnboardingScreenLayout` (like the existing ones) rather than a bare `View`, or you'll lose this for free.
- **Nutrient education copy lives in `src/data/education/`, separate from `src/engine`/`src/data/dri`.** `macroExplanations.ts` holds the plain-language "what it does / why your number is what it is (per goal) / too little / too much" content for the three free macros (PRD §8.4, §8.5), reached via the `MacroDetail` modal route (`src/screens/MacroDetailScreen.tsx`) from `ResultsScreen`. Its tests only check completeness (every macro × every `Goal` has non-empty text) — content edits are a copy review, not a logic change, and don't need new test cases unless you add a macro or a goal. Micronutrient explanations belong in the same directory once the premium/entitlement system exists to gate them (milestone 5) — don't wire micronutrient values/explanations into free-tier UI before then.
- **Animation primitives live in `src/components/` (`AnimatedNumber`, `AnimatedFillBar`, `FadeInView`, `CelebrationBanner`), all built on React Native's built-in `Animated` API — no `react-native-reanimated`/`react-native-svg`/Lottie dependency has been added.** Don't add one without an explicit request; if a future need (e.g. an actual progress *ring*) genuinely requires `react-native-svg`, that's a deliberate call to make then, not a default. Every one of these primitives checks `AccessibilityInfo.isReduceMotionEnabled()` and skips straight to the end state when it's on — keep that pattern for any new animation. `ResultsScreen`'s celebratory banner is gated by the `justCompleted` param on the `Results` route (set only by `GoalScreen` after finishing/re-finishing the wizard) — don't make it fire on ordinary navigations to Results (e.g. app launch with an existing profile), since PRD §11.3 frames it as a "reveal" moment, not a persistent UI element.
- **Illustration assets live in `assets/illustrations/`, AI-generated (not hand-drawn) rather than sourced from an icon library, so the whole set can stay visually consistent.** Style to match if you generate more: friendly rounded flat-vector "kawaii" characters (simple dot eyes, a smile), thick clean outlines, soft flat shading, no text/letters, no clinical or medical iconography, brand green (`palette.green` `#2ECC71`) as an accent somewhere in the composition, off-white (`palette.offWhite` `#F7F9F8`) background. Macro icons additionally sit inside a solid-color circular badge (one accent color per macro, matched in code by `MACRO_VISUALS` in `ResultsScreen.tsx`) so a new icon should follow that same badge convention. Only macro icons + the welcome hero exist so far; the full micronutrient icon set (PRD §11.3) is intentionally deferred until that section has real, unlocked UI to place them in (milestone 5) rather than the current name + lock row.
- **The "has anything changed?" nudge (PRD §8.1) is split the same way as everything else here: pure logic in `src/profile/nudge.ts` (`shouldShowChangeNudge`, `NUDGE_THRESHOLD_DAYS`, fully unit-tested against fixed dates), persistence in `src/storage/nudgeStorage.ts` (also unit-tested), and a thin untested React hook (`src/profile/useChangeNudge.ts`) that wires the two together for `ResultsScreen`.** The stored value is the profile's `updatedAt` at the time of dismissal, not a boolean — this is deliberate: it makes an edited profile (new `updatedAt`) automatically eligible for the nudge again on its own fresh 30-day clock, with no separate "has the profile changed since dismissal" check needed. If you touch this, keep that property (don't switch to a plain dismissed-boolean) and keep the tone soft/dismissible per PRD §11.1 — no alarm colors, no push notifications, no non-dismissible banners.
