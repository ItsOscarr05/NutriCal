# NutriCal — Agent Notes

Personalized daily macro/micronutrient targets app (Expo + React Native + TypeScript). Full spec: `project-docs/PRD.md`. See `README.md` for stack, structure, and current status.

Key constraints to respect when working in this repo:

- **No accounts, no backend, no cloud sync.** Profile data is local-only (`AsyncStorage`). Don't add a server or auth system without an explicit request — this is a deliberate v1 decision (PRD §8.1, §12, §13).
- **Calculation engine (`src/engine`, `src/data/dri`) must stay pure and unit-tested.** It's the credibility core of the product (PRD §10, §14) — no UI concerns leaking in, no unvalidated formula changes without updating/adding tests in `__tests__`. This includes any *new* presentational screen: e.g. `ScienceBreakdownScreen`'s BMR/NEAT/Exercise/TEF energy-source breakdown only pulls real `bmr`/`tdee`/`calorieTarget` numbers from `calculateNutrientTargets`; the NEAT/Exercise/TEF sub-split of "active calories" (`tdee - bmr`) has no engine-level formula behind it, so it's a fixed, clearly-labeled illustrative ratio kept local to that screen — don't promote it into `src/engine` as if it were validated, and don't add a new screen's UI-only math there either.
- **DRI micronutrient data (`src/data/dri/adultBrackets.ts`, `adolescentBrackets.ts`) covers ages 9+ (both sexes) but is still explicitly flagged as needing verification against the NIH ODS DRI tables** before it's treated as production-accurate — don't assume it's audited. Ages below `MIN_SUPPORTED_AGE` (9, exported from `src/data/dri/index.ts`) and pregnancy/lactation life stages are not seeded at all.
- **Tone/design:** plain-language, non-judgmental, no red/green alarm framing (PRD §11.1) — this now extends to *comparative* content too (e.g. `ScienceBreakdownScreen`'s "personalized vs. crash diets" section uses the muted `theme.error`/`errorNeutral` tone, never a vivid red, even when describing a generic risky approach). Light mode = white + green accent; dark mode = navy + green accent (PRD §11.2). **The palette in `src/theme/colors.ts` was fully rebuilt from the Stitch-mockup design system** (Material Design 3-style tokens: `primary`/`primaryContainer`/`primaryFixed`, `secondary`/`tertiary` families, `surfaceContainer*` tiers, etc.) — every pairing was numerically re-validated against WCAG AA and the ratios are documented in the audit comment at the top of that file. The `ThemeColors` field *names* (`background`, `surface`, `accent`, `accentDeep`, `textPrimary`, `textSecondary`, `border`, plus the new M3-style fields) are the stable contract the rest of the app codes against — don't change a hex value, and don't rename/remove a field, without re-running `src/theme/__tests__/contrast.test.ts`. Note `theme.accentDeep` flips which end of the lightness scale it sits at between light and dark mode, which is why a separate `theme.onAccentFixed`/`onAccentDeep`-style field exists for text drawn on top of it — don't hardcode a text color assumption on that background across both themes.
- **Freemium boundary:** macros are always free; micronutrients are premium-gated and shown to free users as a locked, name-only teaser (PRD §7, §8.4) — don't leak micronutrient values to free users in UI work. `MicronutrientExplorerScreen` (the `Micros` tab) is the concrete implementation: it deliberately diverges from the Stitch mockup it was built from, which shows real RDA percentages, progress bars, and "where to get it in real food" drawers to everyone — none of that exists here yet (no premium/entitlement system, and no micronutrient education copy written — see the `src/data/education` bullet below). Cards show only a nutrient's name/category/decorative emoji plus a lock glyph; don't wire in `getAllMicronutrientTargets`/DRI amounts, percentages, or food-source content on this screen until the entitlement system exists.
- **Profile persistence goes through `src/storage/profileStorage.ts` only** — screens/state should call `saveProfile`/`loadProfile`/`clearProfile` rather than touching `AsyncStorage` directly, so the storage format changes in one place. There are exactly two save call sites: `MetabolicForecastScreen.handleFinish` (first-time onboarding) and `QuickAssessmentScreen.handleFinish` (editing from the `Assess` tab) — see below.
- **Units:** height/weight inputs (the onboarding Body Composition page and the `Assess` tab) are imperial-first (ft/in, lb) with a metric toggle. Internal storage (`UserProfile.heightCm`/`weightKg`) is always metric — convert at the UI edge (`src/onboarding/unitConversion.ts`), not in the engine or storage layer.
- **First-time onboarding and editing are two separate UIs.** First-time onboarding is a paged native stack (`src/navigation/OnboardingStack.tsx`, the root `Onboarding` route, screens in `src/screens/onboarding/`): Sex → Age → Body Composition → Daily Motion → Target Outcome → Metabolic Forecast, one question per page, sliding in with the native-stack `slide_from_right` animation (no extra animation library). In-progress answers live in `OnboardingDraftContext` (`src/onboarding/OnboardingDraftContext.tsx`), a provider scoped to that stack only (not `App.tsx`). Sex starts unselected and age starts as an empty text box (number pad, parsed/validated by the unit-tested `src/onboarding/ageInput.ts`), so Next stays disabled until each is answered. The Sex page's blue/pink colors are local to that screen, not theme tokens. `MetabolicForecastScreen.handleFinish` saves and does `navigation.getParent().reset` into `Main` with `justCompleted` (see the animations bullet below). Editing is the single-scroll `QuickAssessmentScreen`, mounted only as the `Assess` tab (sliders/pills, no `TextInput`s), seeding its local `useState` from `profile` and navigating to the sibling `Targets` tab on save. Shared controls (body composition sliders + BMI, activity cards, goal pills, forecast card) and their option lists live in `src/onboarding/ui/AssessmentFields.tsx` and `src/onboarding/assessmentOptions.ts` so the two UIs don't drift. If you add a new profile field, add it to both: a draft field + onboarding page (and `MetabolicForecastScreen`'s save), and seed-from-`profile` + `nextProfile` in `QuickAssessmentScreen`, or one path will silently drop it.
- **The persistent bottom tab bar (`Targets` / `Assess` / `Micros` / `Science`, `src/navigation/MainTabs.tsx`) is the app's navigation shell**, replacing the old single-flow "onboard once, land on one Results screen" stack. `RootStackParamList` (`src/navigation/types.ts`) is now just `Welcome → Onboarding → Main` (which renders `MainTabs`) plus the `MacroDetail` and `Settings` modals — `Main`'s own tabs live in the separate `MainTabParamList`, and the onboarding pages in `OnboardingStackParamList`. A screen nested inside `MainTabs` that needs to act on the root stack (e.g. `ResultsScreen` opening the `Settings` modal or the `MacroDetail` modal) types its navigation prop as a `CompositeNavigationProp<BottomTabNavigationProp<MainTabParamList, '...'>, NativeStackNavigationProp<RootStackParamList>>` — follow that pattern rather than casting to `any` (`QuickAssessmentScreen` uses it too, now that it only mounts as the `Assess` tab). Onboarding pages type theirs as `NativeStackNavigationProp<OnboardingStackParamList, '...'>`.
- **`RootNavigator`'s initial route depends on `ProfileContext.isLoading`/`profile`** (`Main` if a profile exists, `Welcome` otherwise) — don't add new "first screen" logic elsewhere; that's the one place that decides it on launch.
- **`AppSettingsContext` (`src/settings/AppSettingsContext.tsx`, backed by `src/storage/appSettingsStorage.ts`) is one of two top-level contexts**, sitting above `ProfileContext` in `App.tsx` (inside `SafeAreaProvider`) — same split as everywhere else in this repo: pure types/defaults in `src/settings/appSettings.ts` (unit-tested), a thin untested React context exposing `{ settings, isLoading, setUnits, setAppearance }`. (`OnboardingDraftContext` is deliberately *not* top-level — it's scoped to `OnboardingStack`, see above.) It holds `units` (`'imperial' | 'metric'`) and `appearance` (`'light' | 'dark' | 'system'`), both defaulting to today's de-facto behavior (`imperial`, `system`) so no existing install sees a change until the user visits Settings. `useTheme()` (`src/theme/index.ts`) reads `appearance` and only falls back to `useColorScheme()` when it's `'system'`. `QuickAssessmentScreen` seeds its local unit toggle from `settings.units` and calls `setUnits(...)` on change (the onboarding Body Composition page reads/writes `settings.units` directly), so a preference set in any of those places or Settings stays in sync everywhere else — don't reintroduce a hardcoded `'imperial'` default there. **This is not what "Delete my data" clears** — see the Settings screen note below.
- **The Settings screen (`src/screens/SettingsScreen.tsx`) is a modal reached via `GearButton` (`src/components/GearButton.tsx`, an outlined `Ionicons` `"settings-outline"` glyph) placed top-right on `ResultsScreen`/the `Targets` tab only** — there's no per-screen native header in this app (`headerShown: false` everywhere), so the icon is a hand-positioned absolute sibling offset by `useSafeAreaInsets().top`, same pattern as `CelebrationBanner`. Its "Delete my data" action calls `clearProfile()` + `clearDismissedNudgeTimestamp()` only — it deliberately does **not** touch `AppSettingsContext`'s units/appearance preferences, since those are app configuration, not the sensitive body-metric "your data" PRD §13 is about. Its "Edit profile" row navigates to `navigation.navigate('Main', { screen: 'Assess' })` (the nested-navigator params form, since `Settings` is a root-level modal reaching into the tab shell) — the same destination `ResultsScreen`'s own "Edit profile"/"Recalibrate" action reaches via a plain sibling `navigate('Assess')`. If you change this flow, keep both call sites pointed at the same tab rather than reintroducing a shared hook for it.
- **Nutrient education copy lives in `src/data/education/`, separate from `src/engine`/`src/data/dri`.** `macroExplanations.ts` holds the plain-language "what it does / why your number is what it is (per goal) / too little / too much" content for the three free macros (PRD §8.4, §8.5), reached via the `MacroDetail` modal route (`src/screens/MacroDetailScreen.tsx`) from the `Targets` tab. Its tests only check completeness (every macro × every `Goal` has non-empty text) — content edits are a copy review, not a logic change, and don't need new test cases unless you add a macro or a goal. Micronutrient explanations (what it does, food sources, etc.) belong in the same directory once the premium/entitlement system exists to gate them (milestone 5) — don't wire micronutrient values/explanations into free-tier UI before then (see the `MicronutrientExplorerScreen` bullet above).
- **Animation primitives live in `src/components/` (`AnimatedNumber`, `AnimatedFillBar`, `FadeInView`, `CelebrationBanner`, `CircularProgress`, `Mascot`), all built on React Native's built-in `Animated` API.** `react-native-svg` was added (user-approved, v1.1 Stitch redesign) specifically for `CircularProgress` (an SVG progress ring, animates `strokeDashoffset` via `Animated.createAnimatedComponent(Circle)` rather than relying on `style.transform`) and `Mascot` (the ported illustration character) — it's now an established dependency, not a one-off; don't add `react-native-reanimated` or Lottie on top of it without an explicit ask. Every primitive here checks `AccessibilityInfo.isReduceMotionEnabled()` and skips straight to the end state when it's on — keep that pattern for any new animation. The celebratory banner is gated by the `justCompleted` param on the `Targets` route in `MainTabParamList` (set only by `MetabolicForecastScreen.handleFinish` at the end of first-time onboarding — saving edits from `Assess` doesn't set it) — don't make it fire on ordinary navigations to that tab (e.g. app launch with an existing profile, or switching tabs), since PRD §11.3 frames it as a "reveal" moment, not a persistent UI element.
- **Brand mark lives in `assets/` (`logo.png` plus Expo icon/splash/favicon variants).** `nutrical_logo_transparent.png` is the single master artwork; every other brand PNG is generated from it (trimmed, centered on a square canvas — transparent for `logo.png`/splash/favicon/Android foreground, a white silhouette for the Android monochrome layer, and flattened onto mint `#E8F8EE` for the opaque iOS `icon.png`). Regenerate them all from that file rather than editing one variant. The isometric green calculator-with-leaves is the app icon, Android adaptive-icon layers, web favicon, splash image, and the in-app `Logo` component (`src/components/Logo.tsx`) used on Welcome and Settings. Don't swap those files for a different mark without updating every consumer (`app.json` + `Logo.tsx`).
- **Illustration assets live in `assets/illustrations/`, AI-generated (not hand-drawn) rather than sourced from an icon library.** The welcome-hero PNG remains as a bitmap illustration (currently unused by Welcome, which shows the brand `Logo` instead) — the three macro PNG icons (protein/carbs/fat) were removed in the v1.1 Stitch redesign in favor of `MaterialIcons` glyphs inside a colored circular badge (`MACRO_VISUALS` in `ResultsScreen.tsx` now maps each macro to an icon *name*, not an asset `require`); `Mascot` is a hand-ported `react-native-svg` illustration rather than a raster asset. If you generate a new bitmap illustration (e.g. a future hero variant), match the welcome-hero style: friendly rounded flat-vector "kawaii" characters (simple dot eyes, a smile), thick clean outlines, soft flat shading, no text/letters, no clinical or medical iconography, brand green as an accent, off-white background. The full micronutrient icon set (PRD §11.3) is still intentionally deferred until that section has real, unlocked UI to place them in (milestone 5) — `MicronutrientExplorerScreen` currently uses plain decorative emoji per nutrient, explicitly not a custom illustration set, since the values behind them are still locked.
- **The "has anything changed?" nudge (PRD §8.1) is split the same way as everything else here: pure logic in `src/profile/nudge.ts` (`shouldShowChangeNudge`, `NUDGE_THRESHOLD_DAYS`, fully unit-tested against fixed dates), persistence in `src/storage/nudgeStorage.ts` (also unit-tested), and a thin untested React hook (`src/profile/useChangeNudge.ts`) that wires the two together for the `Targets` tab (`ResultsScreen`).** The stored value is the profile's `updatedAt` at the time of dismissal, not a boolean — this is deliberate: it makes an edited profile (new `updatedAt`) automatically eligible for the nudge again on its own fresh 30-day clock, with no separate "has the profile changed since dismissal" check needed. If you touch this, keep that property (don't switch to a plain dismissed-boolean) and keep the tone soft/dismissible per PRD §11.1 — no alarm colors, no push notifications, no non-dismissible banners.
