# NutriCal — Agent Notes

Personalized daily macro/micronutrient targets app (Expo + React Native + TypeScript). Full spec: `project-docs/PRD.md`. See `README.md` for stack, structure, and current status.

Key constraints to respect when working in this repo:

- **No accounts, no backend, no cloud sync.** Profile data is local-only (`AsyncStorage`). Don't add a server or auth system without an explicit request — this is a deliberate v1 decision (PRD §8.1, §12, §13).
- **Calculation engine (`src/engine`, `src/data/dri`) must stay pure and unit-tested.** It's the credibility core of the product (PRD §10, §14) — no UI concerns leaking in, no unvalidated formula changes without updating/adding tests in `__tests__`.
- **DRI micronutrient data (`src/data/dri/adultBrackets.ts`, `adolescentBrackets.ts`) covers ages 9+ (both sexes) but is still explicitly flagged as needing verification against the NIH ODS DRI tables** before it's treated as production-accurate — don't assume it's audited. Ages below `MIN_SUPPORTED_AGE` (9, exported from `src/data/dri/index.ts`) and pregnancy/lactation life stages are not seeded at all.
- **Tone/design:** plain-language, non-judgmental, no red/green alarm framing (PRD §11.1). Light mode = white + green accent; dark mode = navy + green accent (PRD §11.2) — colors in `src/theme/colors.ts` are WCAG AA-validated (see the audit comment at the top of that file); don't change a hex value without re-running `src/theme/__tests__/contrast.test.ts`.
- **Freemium boundary:** macros are always free; micronutrients are premium-gated and shown to free users as a locked, name-only teaser (PRD §7, §8.4) — don't leak micronutrient values to free users in UI work.
- **Profile persistence goes through `src/storage/profileStorage.ts` only** — screens/state should call `saveProfile`/`loadProfile`/`clearProfile` rather than touching `AsyncStorage` directly, so the storage format changes in one place.
- **Units:** onboarding height/weight input is imperial-first (ft/in, lb) with a metric toggle. Internal storage (`UserProfile.heightCm`/`weightKg`) is always metric — convert at the UI edge (`src/onboarding/unitConversion.ts`), not in the engine or storage layer.
- **Two separate state layers, don't conflate them:** `OnboardingDraftContext` (in-memory only) holds in-progress answers *during* the onboarding wizard; `ProfileContext` (backed by `profileStorage`) holds the one real, saved `UserProfile` the rest of the app reads. Only the final onboarding screen (`GoalScreen`) should ever call `saveProfile` to turn a draft into a real profile.
- **Editing an existing profile reuses the onboarding wizard.** `ResultsScreen.handleEditProfile` calls `hydrateFromProfile` on `OnboardingDraftContext` to seed the draft from the saved profile, then navigates forward to `Sex` — it does **not** call `clearProfile`. The saved profile stays intact (and non-null) for the whole edit, only getting overwritten if the user reaches `GoalScreen` and finishes. Each onboarding screen already initializes its local input state from `draft.*`, so this prefills automatically. `GoalScreen` derives `isEditing` from `useProfile().profile !== null` — true only during a re-edit (it's null during first-time onboarding) — to swap its button label to "Save changes." If you add a new onboarding screen/field, make sure it also seeds from `draft` on mount and that `hydrateFromProfile` copies that field, or edits will silently drop it.
- **`RootNavigator`'s initial route depends on `ProfileContext.isLoading`/`profile`** — don't add new "first screen" logic elsewhere; that's the one place that decides Welcome vs. Results on launch.
- **Nutrient education copy lives in `src/data/education/`, separate from `src/engine`/`src/data/dri`.** `macroExplanations.ts` holds the plain-language "what it does / why your number is what it is (per goal) / too little / too much" content for the three free macros (PRD §8.4, §8.5), reached via the `MacroDetail` modal route (`src/screens/MacroDetailScreen.tsx`) from `ResultsScreen`. Its tests only check completeness (every macro × every `Goal` has non-empty text) — content edits are a copy review, not a logic change, and don't need new test cases unless you add a macro or a goal. Micronutrient explanations belong in the same directory once the premium/entitlement system exists to gate them (milestone 5) — don't wire micronutrient values/explanations into free-tier UI before then.
